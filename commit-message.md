# Goals

Prepare `perly.y` and `toke.c` to change the parsing algorithm to GLR.

## Reasons to switch to GLR

The GLR algorithm can parse grammars that are not LALR(1), such as ambiguous
grammars or LALR(n>1) grammars. That is achieved by its capability to track
multiple branches simultaneously.

GLR supports semantic predicates: include/exclude branches based on state variables,
e.g., future enable flags.

### Use-case: Solve block-or-hashref ambiguity

- https://www.perlmonks.org/?node_id=958673
- https://www.nntp.perl.org/group/perl.perl5.porters/2025/07/msg270132.html

```
$hash = map { "key_$_" => $raw->{$_} } keys %$raw;
```

Currently, Perl attempts to resolve what `{` means by looking ahead.
As a result, the aforementioned expression causes a syntax error when Perl incorrectly
guesses that `map` is followed by a hashref.

GLR solution (to explain how this works; the real rule will require fine-tuning):
```
hashref: "{" expression "}" ;
block  : "{" remember statements "}" ;

map_expression:
    | KW_MAP block list_expression
    | KW_MAP hashref COMMA list_expression
    ;
```

How it works:
- Upon receiving a `{` token after KW_MAP, parser will start tracking new branches, let's name them `block` and `hashref`
  - Any `hashref` also constitutes a valid `block`
- The winning branch is determined when:
  - Content no longer matches `expression`, causing the `hashref` branch to be abandoned
  - After `}`:
    - A `COMMA` token abandons the `block` branch
    - Any other token abandons the `hashref` branch

Semantic action execution is postponed until it becomes clear which branch will succeed.
In this case, the crucial factor is the `remember` call to `block_start`.

### Use-case: Sub vs Sub-named vs Sub-sig vs Sub-named-sig

Currently, `toke.c` returns four different tokens when encountering `sub`:
- For subs with signature feature enabled:
  - `KW_SUB_named_sig`
  - `KW_SUB_anon_sig`
- For subs without signature feature enabled:
  - `KW_SUB_named`
  - `KW_SUB_anon`

#### Statement vs expression

- `named` tokens represent statements
- `anon` tokens represent expressions

An LALR(2) grammar would be required to distinguish them in the grammar (yey, GLR provides LALR(n)...).

#### Signatures vs non-signatures

Current grammar (extrapolated):
```
sub_bare_statement:
    : KW_SUB_named     subname startsub proto subattrlist subbody
	| KW_SUB_named_sig subname startsub       subattrlist remember subsignature subbody
    ;
```

With a GLR parser, it becomes possible to express such distinctions in the grammar using semantic conditions:
```
sub_bare_statement:
    : {? ! FEATURE_SIGNATURES_IS_ENABLED ?} KW_SUB subname startsub proto subattrlist subbody
	| {?   FEATURE_SIGNATURES_IS_ENABLED ?} KW_SUB subname startsub       subattrlist remember subsignature subbody
    ;
```

GLR parser discards affected braches when semantic condition evaluates to false.

# Preparation for GLR parser

Unlike the existing `perly.y`, which is based on early bison's yacc parser,
the GLR parser should be fully generated by `bison`.

Therefore, the first step should be "bison-ification" of the current parser
so that Perl can be built using an entirely bison-generated grammar,
eliminating the need for custom `perly.c` and `regen_perly.pl`.

Note:
```
bison -d -v --output=bison-perly-lalr.tab.c --defines=bison-perly-lalr.tab.h --verbose --report-file=bison-perly-lalr.output perly.y
```

# Bison-ification of perly.c

Modification of (primarily) `perly.y` and `perly.c` to make their behavior bison-compatible
so that perly.c can eventually be generated by bison.

Sorted by implementation order.

## YYFPRINTF

Bison's code uses customizable (macro) code to output various messages
to hardcoded `stderr`, whereas `perly.y` uses `Perl_debug_log`.

Change:
Since usage of `__VA_ARGS__` is now allowed in Perl source code, it is possible to define `YYFPRINTF` as a function-like macro replacing its first argument.

## api.prefix

Apart from being good practice (and enabling the capability to use multiple bison grammars in a project), prefix provides a convenient way to implement wrappers required by `api.pure` and `pTHX` sections.

Change:
- Rename current `Perl_yyparse`, `Perl_yylex`, and other yy/YY symbols to behave as if using api.prefix `Perl_parser`
- Create wrapper functions `Perl_yyparse` and `Perl_yylex` to resolve impedance between bison-generated code and Perl code

## api.pure

Pure API is bison's approach to handling multithreading.

The current parser implementation uses Perl's own parser status structure to handle `yylval` properly.

This luxury will not be available when using a bison-generated parser, so the current API should be adapted to bridge the bison approach with the Perl approach.

Change:
- Decompose the current `Perl_yylex` (see api.prefix):
  - The current `Perl_yylex` will call `Perl_yylex` in the bison way
  - The new function will have bison generated API

## pTHX

Perl uses macros to pass (if any) thread-safety data through functions, while bison requires such parameters to be always present.

Change:
- (see api.prefix) Split `Perl_yyparse` and `Perl_yylex` functions
- perly.y: include `%params { tTHX aTHX }`
- When pTHX evaluates to empty, declare type tTHX as `void *`

## %destructor

`bison` offers the capability to declare functions to destroy discarded `yylval`.

When an error occurs, not only one, but possibly many `opval` non-terminals should be freed.

Solution:
- Use `%destructor` to register code to clean up discarded symbols

Change:
